# Releasing MadaraMaster

[English](#english) · [Español](#español)

## English

Releases are built and published by [`.github/workflows/release.yml`](.github/workflows/release.yml) when a tag `v*` is pushed. Nobody uploads files by hand.

### What the workflow does

1. **Check version** — the tag must be `v` + `madaramaster.__version__` (e.g. `v5.1.0` for `__version__ = "5.1.0"`); otherwise the run stops before building anything. Versions with `a`, `b`, `rc` or `dev` are published as pre-releases.
2. **CI** — the full test matrix (Linux, Windows, macOS × Python 3.10/3.12), lint and the Windows build, reusing `ci.yml`.
3. **Build wheel and sdist** — `python -m build`, `twine check --strict`, the test suite run from the extracted sdist, and the wheel installed in a clean venv.
4. **Build Windows executable** — PyInstaller, smoke test (`--help`, `version`), named `MadaraMaster-<version>-windows-x64.exe`.
5. **GitHub Release** — attaches the `.exe`, the wheel and the sdist. The notes list the commits since the previous `v*` tag, a link to the full diff and the SHA-256 of every file (generated by [`scripts/release_notes.py`](scripts/release_notes.py)).
6. **Publish to PyPI** — uploads the wheel and the sdist with [Trusted Publishing](https://docs.pypi.org/trusted-publishers/): GitHub issues a short-lived OIDC token to this job only; no API token is stored anywhere.

Steps 5 and 6 only run after 2–4 succeed, and are independent of each other: if PyPI is not configured yet, the GitHub Release is still created.

### Cutting a release

1. Update `__version__` in `madaramaster/__init__.py` in a pull request and merge it.
2. Tag the merge commit on `main` and push the tag:

   ```bash
   git checkout main && git pull
   git tag -a v5.1.0 -m "MadaraMaster 5.1.0"
   git push origin v5.1.0
   ```

3. Follow the run under **Actions → Release**. The `pypi` job waits for approval if the `pypi` environment has required reviewers.

A tag that does not match `__version__` fails in the first job; delete it (`git push --delete origin vX.Y.Z`), fix the version and tag again. PyPI never accepts the same version twice, so a published version cannot be replaced — release a new one instead.

### One-time PyPI setup (Trusted Publishing)

See the Spanish section below for the same steps in Spanish.

1. Sign in to <https://pypi.org> (create an account and enable 2FA if needed).
2. Go to **Your account → Publishing → Add a new pending publisher** (<https://pypi.org/manage/account/publishing/>). A *pending* publisher reserves the name and lets the first upload create the project.
3. Fill in, exactly:
   - **PyPI Project Name:** `madaramaster`
   - **Owner:** `jaimefgdev`
   - **Repository name:** `MadaraMaster`
   - **Workflow name:** `release.yml`
   - **Environment name:** `pypi`
4. Click **Add**.
5. On GitHub, create the environment: **Settings → Environments → New environment → `pypi`**. Recommended: add yourself under **Required reviewers** (every PyPI upload then waits for your click) and, under **Deployment branches and tags**, allow only tags matching `v*`.
6. Push a tag as described above. After the first successful upload the project exists on PyPI and the pending publisher becomes a normal one (visible under the project's **Settings → Publishing**).

Optional: to rehearse on TestPyPI, register the same pending publisher on <https://test.pypi.org> with environment `testpypi`, and add a job that uses `pypa/gh-action-pypi-publish` with `repository-url: https://test.pypi.org/legacy/`.

## Español

Las versiones se construyen y publican con [`.github/workflows/release.yml`](.github/workflows/release.yml) al subir un tag `v*`. Nadie sube ficheros a mano.

### Qué hace el workflow

1. **Comprobar la versión**: el tag debe ser `v` + `madaramaster.__version__` (p. ej. `v5.1.0` para `__version__ = "5.1.0"`); si no, se detiene antes de construir nada. Las versiones con `a`, `b`, `rc` o `dev` se publican como pre-release.
2. **CI**: la matriz completa de tests (Linux, Windows, macOS × Python 3.10/3.12), el lint y el build de Windows, reutilizando `ci.yml`.
3. **Wheel y sdist**: `python -m build`, `twine check --strict`, los tests ejecutados desde el sdist extraído y el wheel instalado en un venv limpio.
4. **Ejecutable de Windows**: PyInstaller, prueba de humo (`--help`, `version`) y nombre `MadaraMaster-<versión>-windows-x64.exe`.
5. **GitHub Release**: adjunta el `.exe`, el wheel y el sdist. Las notas listan los commits desde el tag `v*` anterior, un enlace al diff completo y el SHA-256 de cada fichero (las genera [`scripts/release_notes.py`](scripts/release_notes.py)).
6. **Publicar en PyPI**: sube el wheel y el sdist con [Trusted Publishing](https://docs.pypi.org/trusted-publishers/): GitHub emite un token OIDC de corta duración solo para ese job; no se guarda ningún token de API.

Los pasos 5 y 6 solo se ejecutan si 2–4 terminan bien, y son independientes entre sí: si PyPI aún no está configurado, la GitHub Release se crea igualmente.

### Publicar una versión

1. Actualiza `__version__` en `madaramaster/__init__.py` en un pull request y fusiónalo.
2. Crea el tag sobre el commit de `main` y súbelo:

   ```bash
   git checkout main && git pull
   git tag -a v5.1.0 -m "MadaraMaster 5.1.0"
   git push origin v5.1.0
   ```

3. Sigue la ejecución en **Actions → Release**. El job `pypi` espera tu aprobación si el entorno `pypi` tiene revisores obligatorios.

Si el tag no coincide con `__version__`, falla el primer job: bórralo (`git push --delete origin vX.Y.Z`), corrige la versión y vuelve a crear el tag. PyPI nunca acepta dos veces la misma versión, así que una versión publicada no se puede reemplazar: publica una nueva.

### Configuración única en PyPI (Trusted Publishing)

1. Entra en <https://pypi.org> (crea una cuenta y activa la verificación en dos pasos si hace falta).
2. Ve a **Your account → Publishing → Add a new pending publisher** (<https://pypi.org/manage/account/publishing/>). Un publicador *pendiente* reserva el nombre y permite que la primera subida cree el proyecto.
3. Rellena exactamente:
   - **PyPI Project Name:** `madaramaster`
   - **Owner:** `jaimefgdev`
   - **Repository name:** `MadaraMaster`
   - **Workflow name:** `release.yml`
   - **Environment name:** `pypi`
4. Pulsa **Add**.
5. En GitHub, crea el entorno: **Settings → Environments → New environment → `pypi`**. Recomendado: añádete en **Required reviewers** (cada subida a PyPI esperará tu clic) y, en **Deployment branches and tags**, permite solo tags que coincidan con `v*`.
6. Sube un tag como se describe arriba. Tras la primera subida correcta el proyecto existe en PyPI y el publicador pendiente pasa a ser uno normal (visible en **Settings → Publishing** del proyecto).

Opcional: para ensayar en TestPyPI, registra el mismo publicador pendiente en <https://test.pypi.org> con el entorno `testpypi` y añade un job que use `pypa/gh-action-pypi-publish` con `repository-url: https://test.pypi.org/legacy/`.
